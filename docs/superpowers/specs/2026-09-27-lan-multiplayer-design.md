## 1. 背景与目标

现有 `tank-battle-cpp` 是 Scratch 3《坦克大战》的忠实单机移植。本设计新增一个
**局域网 1v1 玩家对战模式**：同一局域网内两台 Windows 电脑，一人创建对局、
一人加入，各操控一辆坦克互相射击，3 血制一局定胜负。

**硬约束**：

- 单人模式的行为零改动（.sb3 忠实性原则，现有回归测试必须保持全绿）；
- 不引入新第三方依赖：sfml-network 已因语音控制在链路与 DLL 闭包（25 个）中；
- 两台机器运行**同一份构建产物**（同一目录拷贝过去），这是本方案的前提假设；
- `lessons/` 教学线不受影响（不改动 `scratch_like.hpp` 依赖的接口）。

## 2. 已确认的决策

| 决策点 | 结论 | 备注 |
|---|---|---|
| 对战形态 | 1v1 玩家互射，无 AI 敌人 | 维护者选定的解读 |
| 胜负规则 | 血量制：各 3 血，被导弹击中扣 1 血，扣尽判负 | 数值为新增，非 .sb3 来源，见 §5.2 |
| 同步模型 | 主机权威 + 快照同步（方案 A） | 否决了帧同步锁步（desync 脆弱）与客户端预测（局域网延迟本就无感） |
| 组网拓扑 | 一人建主局一人加入，无独立服务器 | 主机 = 玩家 1，客户端 = 玩家 2 |
| 发现机制 | UDP 广播自动发现为主，`--join <ip>` 启动参数兜底 | 不在游戏内做文本输入框 |
| 语音控制 | 联机模式自动可用 | 语音口令归一化为 InputState，属本地输入 |

## 3. 总体架构

```
main.cpp            新增 --join <ip> 参数（任意参数位置；首个非 -- 开头的
                    位置参数仍是 assets 路径，避免与现有 argv[1] 用法冲突）
  └─ Game           现有类，扩展：模式入口 + 大厅/战斗阶段 + 双坦克渲染 + 血条 UI
       ├─（单人模式代码路径原样保留）
       ├─ InputState.hpp   [新增] 一帧玩家意图：移动键位、炮塔角度、开火位
       ├─ Protocol.hpp     [新增] 纯编解码：消息结构体 <-> 字节流，无 socket
       ├─ Battle.hpp/cpp   [新增] PvP 模拟：BattleState + stepBattle()，纯逻辑
       └─ NetSession.hpp/cpp [新增] socket/线程：发现、进房、收发、掉线检测
```

模块依赖方向（单向，禁止反向）：

```
InputState → （无依赖）
Battle     → common.hpp + InputState（仅 <SFML/System.hpp>，可独立单测；
            BattleDefs 就定义在 Battle.hpp 内，不是独立依赖）
Protocol   → InputState（纯字节流编解码，无 socket、无 Graphics）
NetSession → Protocol, InputState（socket 层不进单测）
Game       → 以上全部
```

### BattleDefs：数值注入面（评审 C2 修复）

`Battle.hpp` 定义**纯数据 POD** `BattleDefs`，集中承载 PvP 模拟要用的全部数值：
双方出生点/初始朝向、移动与导弹速度、开火冷却、活动围栏、坦克命中盒
（半宽高 + 盒心相对旋转中心偏移）、血量、爆炸时长、无敌时长、导弹出界边界。

- 运行期由 **Game 在开局时注入**：速度/冷却/围栏取自 `Game.hpp` 现有常量
  （它们是 class 私有 constexpr，外部模块不可见），命中盒取自
  `Assets` 的 `playerBody` 造型元数据（`halfExtents`/`centerOffset`，
  运行期才存在）——Battle 不 include `Assets.hpp`（它会拉进 SFML
  Graphics/Audio，破坏可单测性）。**注意尺寸折算**：`Costume::halfExtents`
  是 100% 尺寸的舞台单位，坦克实际按缩小乘数渲染与判定（与单人
  `makeSprite`/`hitTest` 的 sizePercent 同值）——注入时必须乘上同一乘数，
  否则命中盒放大约 3.3 倍。
- 单元测试用任意小数值构造 BattleDefs，不依赖素材与真实常量。
- §5.2 的 PvP 新增数值也定义在 BattleDefs 里（不放 Game.hpp，避免单人
  常量区混入联机专属值）。

**单人坦克运动代码与 Battle 不共享**：PVP 坦克行为本就不同（中弹不死、重生、
无敌帧），复用约 30 行运动相似逻辑的收益远小于改动单人路径的回归风险。两个
模块共用的是 `common.hpp` 的坐标/方向/旋转盒碰撞/围栏钳制原语（纯几何函数
按参数收盒尺寸，无需 Assets）。此偏离记入 README 已知差异。

### 角色与权威

- 主机（玩家 1，底部出生）：运行 `BattleState` 完整模拟，30Hz 广播快照；
  命中、血量、胜负**只在主机计算**，双端永无分歧。
- 客户端（玩家 2，顶部出生）：30Hz 发送 InputState，收快照直接渲染。
  唯一的本地覆盖：**己方炮塔角度每帧用本地鼠标重算**（纯表现层，主机模拟
  与命中判定用的仍是客户端最近上报的炮塔角度）——否则炮塔跟手会滞后 RTT。

## 4. 联机流程与 UX

标题画面（原版开始画面）保留"点击 = 单人"，画面下方加一行提示文字：
`H 创建联机对战    J 加入对战`（新增文字需重跑 `tools/subset_font.py` 扩字体子集）。

- **H（主机）**：绑定 UDP 52021 → 等待页（显示房间名 = 环境变量
  `COMPUTERNAME`，取不到则 "host"）→ 收到客户端 JOIN → 等待页显示
  "已连接：<客户端名>"（客户端名同样取其 COMPUTERNAME，随 JOIN 上报）→
  双方显示 3-2-1 倒计时（3 秒）→ 开战。
- **J（客户端）**：向 `255.255.255.255:52021` 广播 DISC，扫描 2 秒：
  - 收到 0 个 HOST 回应 → 提示"未发现对局，按 J 重试或用 --join IP 启动"；
  - 收到 1 个 → 直接进；收到多个 → 列表显示房间名，按数字键选择；
  - 选定后进入连接阶段（发 JOIN 5Hz；主机收到第一个 JOIN 即开始倒计时，
    客户端以**第一个到达的 SNAP**（phase=倒计时）为连接成功标志；
    **5 秒未收到任何 SNAP → 退回扫描页**并提示，不发呆等）。
- **结算与重开**：血量耗尽 → 冻结 + 胜者画面（复用 `screen_gameover.jpg`
  叠加"玩家 1 胜利/玩家 2 胜利/平局"文字）→ **双方都按 R** 才重开（客户端
  把 ready 位随 JOIN 上报，主机看到双方 ready 即重置战斗、重新倒计时；
  **tick 跨局单调递增、不清零**，见 §6.2）。战斗中血条旁标注"玩家1(房主)/
  玩家2(加入)"。
- **倒计时显示 = 客户端本地计时**（单调 tick 下无法从 tick 推导剩余秒数）：
  客户端在 phase 变为 0 时启动本地 3 秒倒计时，phase 变为 1 即切战斗画面
  ——本地计时与主机若有零点几秒偏差，以 phase 切换自愈。
- **退出**：战斗/大厅中按 Esc → 发 BYE（尽力而为）→ 关会话回标题；
  对方收到 BYE 或超时（§7）→ 提示"对方已离开" → 回标题。

## 6. 协议规格

全 UDP，主机绑定 **52021**（避开语音 52017/52018），客户端绑随机端口。
多字节字段一律小端。量化约定：坐标=舞台单位×16（i16），角度=度×16
（u16；**编码前先把角度折叠到 [0,360)**——炮塔手转可累积超界，Scratch
方向值本身无环绕约束）。

**核心设计：没有 ack/重传层。** 所有消息都是幂等的"现状广播"：
大厅阶段 5Hz、战斗阶段 30Hz 各自重发当前状态；接收方从持续到达的状态流
推导阶段迁移（例：客户端收到第一个 SNAP 即知连接成功，无需可靠的
START 消息）。丢包容忍：快照丢了等下一个；输入包丢了主机沿用上次输入
——按住键的语义下"沿用上次"恰是正确插值（暂停边界见 §6.3）。

### 6.1 消息表

公共头：`[u8 msgId][u8 version]`。

| msgId | 名称 | 方向 | 频率 | 载荷 |
|---|---|---|---|---|
| 1 | DISC | C→广播 | 扫描期 5Hz | （空） |
| 2 | HOST | H→C 单播 | 仅大厅等待期回应 DISC | 房间名 ≤31B |
| 3 | ERR | H→C | 收到版本不符的 DISC/JOIN，或战斗中收到陌生 JOIN | reason u8（1=版本不符 2=忙）+ 对端 version u8 |
| 4 | JOIN | C→H | 5Hz（大厅/结算期） | 玩家名 ≤31B + ready 位 u8 |
| 5 | INP | C→H | 30Hz（战斗期） | moveBits u8（bit0-3=上/下/左/右）+ aim u16 + fire u8 |
| 6 | SNAP | H→C | 30Hz（倒计时起全程） | 见 §6.2 |
| 7 | BYE | 双向 | 尽力一次 | （空） |
| 8 | KEEP | 双向 | 1Hz（仅后台心跳线程） | （空；**目的端口=对端主接收端口**，见 §6.3） |

### 6.2 SNAP 载荷

```
[u32 tick][u8 phase: 0=倒计时 1=战斗 2=结算 3=暂停]
[u8 hp0][u8 hp1]
[tank0][tank1]        每个: x i16, y i16, dir u16, turret u16,
                       state u8(0=正常 1=爆炸中 2=无敌), animFrame u8(爆炸帧)
[u8 missileCount]     每个: x i16, y i16, dir u16, owner u8(0/1)
[u8 events 位掩码]    b0=玩家0开火 b1=玩家1开火 b2=玩家0被击中
                       b3=玩家1被击中 b4=玩家0阵亡 b5=玩家1阵亡
```

- **tick = 快照序号：每发出一个 SNAP +1，跨局单调、重开与暂停均不清零、
  暂停期世界冻结但 tick 照常前进**（评审 C1/N1 修复）。u32 在 30Hz 下
  约 4.5 年才溢出，无实际风险。暂停期若冻结 tick，迁移到 phase=3 的那个
  SNAP 会与冻结前最后快照 tick 相同、被 `==` 规则整包跳过，"暂停中"标签
  将永远不可见——故 tick 是帧计数而非模拟时间。客户端接受规则保持单一：
  `tick > lastTick` 应用状态并处理事件；`tick == lastTick` 静默跳过
  （重复包，事件不重放）；`tick < lastTick` 丢弃（旧包）。
- 解析校验（任一违反即**整包按坏包丢弃**，安全失败、绝不越界）：截断包、
  未知 msgId；枚举字段 phase>3、state>2、reason>2；missileCount>64；
  **state==1 时 animFrame>5**（客户端把它直接当 6 帧爆炸数组的下标，
  坏值=越界读，这是 SNAP 里唯一作数组下标的字段）；owner>1；hp>3。
- 事件位只属于当帧 tick；若该 SNAP 丢包则该帧音效/爆炸表现缺失（血量
  与位置随下一包自动对齐）——纯表现层损失，可接受，不为此引入可靠性。
- 典型快照约 30+7N 字节（N=导弹数，含公共头），N<10 时约 100B，
  30Hz ≈ 3KB/s。
- INP 在战斗期**无条件 30Hz 发送**（无操作也发全零载荷）——§6.3 的
  暂停判定依赖"收到的是最新心跳化输入"，而非"有按键"。

### 6.3 源地址过滤与暂停语义（评审 I3/I5 修复）

**源地址过滤是正确性要求，不属于反作弊**（§10）：会话建立后，**非对端 IP
的包整包丢弃**（否则局域网内任意 UDP 流量碰巧打来即可伪造 SNAP 改写客户
端状态）。端口规则：**KEEP 之外的包必须来自对端主端口**；**KEEP 接受自
对端 IP 的任意源端口**——心跳走独立 socket、源端口随机，第一个 KEEP
到达前白名单根本无从得知它，若按"只认主端口"实现会把 KEEP 当陌生包丢掉、
5 秒误判断线（语音心跳先例的同款坑）。KEEP 的**目的端口 = 对端主接收
端口**（客户端→主机发 52021；主机→客户端发其主 socket 端口），发去对端
心跳端口会双端互相收不到。

**暂停语义**（拖窗口模态循环的处理）：战斗阶段（phase=1）主机若
**>1 秒未收到 INP 但 KEEP 仍在**（= 对端进程活着但主循环停摆，典型为
拖动/缩放窗口），冻结模拟并把快照 phase 切为 3=暂停——**世界状态冻结但
tick 照常 +1**（§6.2，否则暂停 SNAP 全被 `==` 规则吞掉，标签永不可见）；
暂停期间爆炸动画帧、无敌计时、开火冷却等**一切模拟计时器随模拟冻结**
（一律由模拟步进驱动，禁止墙钟）。INP 恢复即切回 phase=1 继续。倒计时/
结算阶段无输入预期，不适用此规则。两个方向的表现：**客户端拖窗** →
主机发 phase=3，客户端显示"对方暂停中"；**主机拖窗** → 主机发不出任何
SNAP，客户端画面冻结——客户端兜底：**phase=1 下 >1 秒无新 tick 且 KEEP
仍在 → 本地自行显示"暂停中"标签**，保证两个方向都有可见提示。远端真
掉线（连 KEEP 都停）则走 §7 的 5 秒超时。局域网突发丢包 >1s 会触发短暂
暂停，属已知无害行为，记入 README。

### 6.4 发现与进房的忙碌语义（评审 I4 修复）

- 主机**进入倒计时起即停止回应 DISC**（战斗中的主机对局域网扫描不可见，
  避免第三方客户端连上等待）；
- 战斗/倒计时/结算中收到陌生地址的 JOIN → 对**每一份到达的**陌生 JOIN
  回一份 `ERR{reason=2 忙}`（对方 5Hz 重发 JOIN，回应随之重发，天然
  可靠；客户端收到 busy → 提示"对局已满/进行中"退回扫描）；
- 客户端连接阶段 5 秒无 SNAP → 退回扫描页（§4）。

## 7. 容错与边界情况

| 情形 | 处理 |
|---|---|
| 对方 5 秒无任何包（含 KEEP） | 判掉线："对方已离开" → 关会话回标题 |
| 拖动/缩放窗口的 Windows 模态循环 | §6.3：后台 jthread 用**独立 socket** 1Hz 发 KEEP（SFML socket 非线程安全，同 voiceSock/voicePingSock 先例）；INP 停滞 >1s 且 KEEP 活 → 暂停模拟（tick 照增），恢复即续；两个方向均有暂停标签（phase=3 或客户端兜底） |
| 快照/输入乱序或丢包 | SNAP 按 §6.2 接受规则；INP 无序号，最新到达者生效 |
| 陌生地址的包 | 会话建立后按 §6.3 源过滤丢弃（对端 IP + 主端口；KEEP 例外：对端 IP 任意源端口均可） |
| 战斗中第三方 JOIN | §6.4：回 ERR{忙}，不进房 |
| 客户端连接 5s 无 SNAP | 退回扫描页并提示 |
| 重开对局 | 双方 ready → 主机重置战斗、重新倒计时；**tick 单调不清零**（§6.2），客户端接受规则无跨局特判 |
| 客户端加入时版本不符 | 主机回 ERR{版本}，客户端提示"版本不一致，请两台机器使用同一份构建"后退回 |
| 同机第二个实例建主局 | 52021 绑定失败 → 提示"端口被占用（已有机局？）"，回标题 |
| Windows 防火墙首次弹窗 | README 说明需允许（专用网络）；被拒则表现为对方扫不到/连不上 |
| 广播被路由器拦截 | `--join <ip>` 显式指定地址兜底 |
| 中途 Esc / 窗口关闭 | 发 BYE 后立刻清理会话与线程（含心跳线程 join），回标题/退出 |
| 语音助手并存 | 语音端口 52017 未接管时自动禁用（现有逻辑），与联机无冲突；52021 与语音端口不同，无占用冲突 |

## 8. 测试策略

- **单元测试**（进 `tests/unit_tests.cpp`，不碰 socket）：
  - Protocol 编解码：全部消息 round-trip；坐标/角度量化往返误差 ≤1/16
    单位；角度折叠（359.99°→编码→解码不越界）；截断包/未知 msgId/非法

    崩溃；SNAP 接受规则（>应用、=跳过、<丢弃；**暂停期 tick 照增 →

## 10. 明确不做（YAGNI）

- 不做 2 人以上、观战、AI 补位、合作模式；
- 不做互联网穿透（仅局域网/同网段；`--join` 支持任意可达地址属顺带能力，非目标）；
- 不做断线重连（掉线即结束对局）；
- 不做输入加密/反作弊（局域网熟人对战场景）——但**源地址过滤与忙碌
  拒绝是正确性要求，不属反作弊范畴**，已定入 §6.3/§6.4；
- 不做客户端预测/快照插值（局域网 RTT 无感；InputState 抽象已为将来
  升级留好缝，届时另立设计）。
