# 局域网 1v1 对战设计（LAN Multiplayer PvP）

- 日期：2026-09-27
- 分支：`feature/lan-multiplayer`
- 状态：设计定稿（已与维护者逐节确认），待实现计划
- 关联：`tank-battle-cpp/README.md`（对应关系表与已知差异需同步更新）

## 1. 背景与目标

现有 `tank-battle-cpp` 是 Scratch 3《坦克大战》的忠实单机移植。本设计新增一个
**局域网 1v1 玩家对战模式**：同一局域网内两台 Windows 电脑，一人创建对局、
一人加入，各操控一辆坦克互相射击，3 血制一局定胜负。

目标之外明确不做（见 §10）。

**硬约束**：

- 单人模式的行为零改动（.sb3 忠实性原则，现有回归测试必须保持全绿）；
- 不引入新第三方依赖：sfml-network 已因语音控制在链路与 DLL 闭包（25 个）中；
- 两台机器运行**同一份构建产物**（同一目录拷贝过去），这是本方案的前提假设；
- `lessons/` 教学线不受影响（不改动 `scratch_like.hpp` 依赖的接口）。

## 2. 已确认的决策

| 决策点 | 结论 | 备注 |
|---|---|---|
| 对战形态 | 1v1 玩家互射，无 AI 敌人 | 维护者选定的解读 |
| 胜负规则 | 血量制：各 3 血，被导弹击中扣 1 血，扣尽判负 | 命中后爆炸冻结、回出生点、短暂无敌，见 §5 |
| 同步模型 | 主机权威 + 快照同步（方案 A） | 否决了帧同步锁步（desync 脆弱）与客户端预测（局域网延迟本就无感） |
| 组网拓扑 | 一人建主局一人加入，无独立服务器 | 主机 = 玩家 1，客户端 = 玩家 2 |
| 发现机制 | UDP 广播自动发现为主，`--join <ip>` 启动参数兜底 | 不在游戏内做文本输入框 |
| 语音控制 | 联机模式自动可用 | 语音口令归一化为 InputState，属本地输入 |

## 3. 总体架构

```
main.cpp            新增 --join <ip> 参数，其余不动
  └─ Game           现有类，扩展：模式入口 + 大厅/战斗阶段 + 双坦克渲染 + 血条 UI
       ├─（单人模式代码路径原样保留）
       ├─ InputState.hpp   [新增] 一帧玩家意图：移动键位、炮塔角度、开火位
       ├─ Protocol.hpp     [新增] 纯编解码：消息结构体 <-> 字节流，无 socket
       ├─ Battle.hpp/cpp   [新增] PvP 模拟：BattleState + stepBattle()，纯逻辑
       └─ NetSession.hpp/cpp [新增] socket/线程：发现、进房、收发、掉线检测
```

模块依赖方向（单向，禁止反向）：

```
Battle, Protocol, InputState  →  common.hpp（仅 <SFML/System.hpp>，可独立单测）
NetSession                    →  Protocol, InputState（socket 层不进单测）
Game                          →  以上全部
```

**单人坦克运动代码与 Battle 不共享**：PVP 坦克行为本就不同（中弹不死、重生、
无敌帧），复用约 30 行运动相似逻辑的收益远小于改动单人路径的回归风险。两个
模块共用的是 `common.hpp` 的坐标/方向/旋转盒碰撞/围栏钳制原语与 `Assets` 的
造型元数据（命中判定用 `player_body`/`player_turret` 的紧包围盒，与原版敌人
判定同款函数）。此偏离记入 README 已知差异。

### 角色与权威

- 主机（玩家 1，底部出生）：运行 `BattleState` 完整模拟，30Hz 广播快照；
  命中、血量、胜负**只在主机计算**，双端永无分歧。
- 客户端（玩家 2，顶部出生）：30Hz 发送 InputState，收快照直接渲染。
  唯一的本地覆盖：**己方炮塔角度每帧用本地鼠标重算**（纯表现层，主机模拟
  与命中判定用的仍是客户端最近上报的炮塔角度）——否则炮塔跟手会滞后 RTT。

## 4. 联机流程与 UX

标题画面（原版开始画面）保留"点击 = 单人"，画面下方加一行提示文字：
`H 创建联机对战    J 加入对战`（新增文字需重跑 `tools/subset_font.py` 扩字体子集）。

- **H（主机）**：绑定 UDP 52021 → 等待页（显示房间名 = 环境变量
  `COMPUTERNAME`，取不到则 "host"）→ 收到客户端 JOIN → 双方显示 3-2-1
  倒计时 → 开战。
- **J（客户端）**：向 `255.255.255.255:52021` 广播 DISC，扫描 2 秒：
  - 收到 0 个 HOST 回应 → 提示"未发现对局，按 J 重试或用 --join IP 启动"；
  - 收到 1 个 → 直接进；收到多个 → 列表显示房间名，按数字键选择；
  - 选定后进入连接阶段（发 JOIN 5Hz；主机收到第一个 JOIN 即开始倒计时，
    客户端以**第一个到达的 SNAP**（phase=倒计时）为连接成功标志）。
- **结算与重开**：血量耗尽 → 冻结 + 胜者画面（复用 `screen_gameover.jpg`
  叠加"玩家 1 胜利/玩家 2 胜利"文字）→ **双方都按 R** 才重开（客户端把
  ready 位随消息上报，主机看到双方 ready 即重置战斗、tick 归零、重新倒计时）。
- **退出**：战斗/大厅中按 Esc → 发 BYE（尽力而为）→ 关会话回标题；
  对方收到 BYE 或超时（§7）→ 提示"对方已离开" → 回标题。

## 5. 玩法规则（PvP Battle）

数值全部沿用原版单人常量（`Game.hpp` 顶部），不另设一套：

| 项 | 值 | 来源 |
|---|---|---|
| 移动速度 | 每帧 5 步，30Hz | `PlayerSpeed` |
| 导弹速度 | 每帧 10 步 | `MissileSpeed` |
| 开火冷却 | 0.5s（左键/空格，按住连发） | `FireCooldown` |
| 活动围栏 | x∈[-211,205], y∈[-154,150]，双坦克同围栏 | `PlayerMin/Max` |
| 炮塔 | 鼠标永远跟随；←/→ 每秒 180° 手转（移动鼠标交还） | 现有单人行为 |
| 命中判定 | 导弹旋转盒 vs 坦克紧包围盒，同原版敌人判定 | `stage::boxHitTest` |

PvP 特有规则：

- **出生点**：主机方 (0, -120) 底部、炮塔初始朝上（dir=0）；客户端方
  (0, +120) 顶部、炮塔初始朝下（dir=180）。
- **外观区分**：客户端坦克绘制时加蓝色 tint（`sf::Sprite::setColor`），
  主机方保持原色。素材零新增。
- **命中流程**：导弹消失 → 中弹方扣 1 血 → 原地爆炸动画 6 帧×0.1s=0.6s
  （期间**冻结**：不可移动/开火，导弹可穿过）→ 结束后**瞬移回己方出生点**
  （朝向、炮塔也重置）→ **1.5s 无敌**（闪烁渲染，不被判定）。
- **判负**：任一方血量归 0 → 全场冻结 → 胜者画面。
- **导弹出界**即消失（无反弹，同原版导弹行为）。
- **HUD**：左上原"分数"文字替换为双方血条（3 格×2），主机方靠左、
  客户端方靠右，附 H 房主/J 客户端图例文字。

## 6. 协议规格

全 UDP，主机绑定 **52021**（避开语音 52017/52018），客户端绑随机端口。
多字节字段一律小端。所有数值量化约定：坐标=舞台单位×16（i16），
角度=度×16（u16，0..5759）。

**核心设计：没有 ack/重传层。** 所有消息都是幂等的"现状广播"：
大厅阶段 5Hz、战斗阶段 30Hz 各自重发当前状态；接收方从持续到达的状态流
推导阶段迁移（例：客户端收到第一个 SNAP 即知开战，无需可靠的 START 消息）。
丢包容忍：快照丢了等下一个；输入包丢了主机沿用上次输入——按住键的语义
下"沿用上次"恰是正确插值。

公共头：`[u8 msgId][u8 version]`。version 不一致时：主机对 JOIN 回
`ERR{版本}`，客户端显示"版本不一致，请两台机器使用同一份构建"后退出加入流程。

| msgId | 名称 | 方向 | 频率 | 载荷 |
|---|---|---|---|---|
| 1 | DISC | C→广播 | 扫描期 5Hz | （空） |
| 2 | HOST | H→C 单播 | 回应 DISC | 房间名（≤31B） |
| 3 | ERR | H→C | 收到版本不符的 DISC/JOIN 时 | 对端版本号 u8 |
| 4 | JOIN | C→H | 5Hz（大厅/结算期） | 玩家名 ≤31B + ready 位 u8 |
| 5 | INP | C→H | 30Hz | moveBits u8（bit0-3=上/下/左/右）+ aim u16 + fire u8 |
| 6 | SNAP | H→C | 30Hz | 见下 |
| 7 | BYE | 双向 | 尽力一次 | （空） |
| 8 | KEEP | 双向 | 1Hz（仅后台线程） | （空） |

SNAP 载荷：

```
[u32 tick][u8 phase: 0=倒计时 1=战斗 2=结算]
[u8 hp0][u8 hp1]
[tank0][tank1]        每个: x i16, y i16, dir u16, turret u16,
                       state u8(0=正常 1=爆炸中 2=无敌), animFrame u8(爆炸帧)
[u8 missileCount]     每个: x i16, y i16, dir u16
[u8 events 位掩码]    b0=玩家0开火 b1=玩家1开火 b2=玩家0被击中
                       b3=玩家1被击中 b4=玩家0阵亡 b5=玩家1阵亡
```

事件位只属于当帧 tick，客户端用本帧到达的 SNAP 触发音效/爆炸；若该
SNAP 丢包则该帧音效缺失（血量与位置随下一包自动对齐）——纯表现层损失，
可接受，不为此引入可靠性。典型快照 40+16N 字节（N=导弹数），N<10 时
约 200B，30Hz ≈ 6KB/s。

主机收到 INP 即刻生效于下一个 tick（局域网 RTT 典型 <5ms，不做输入缓冲）。

## 7. 容错与边界情况

| 情形 | 处理 |
|---|---|
| 对方 5 秒无任何包 | 判掉线："对方已离开" → 关会话回标题。用 5s 而非 3s，给拖窗口留余量（下条） |
| 拖动/缩放窗口的 Windows 模态循环 | 主循环停摆期间不发包也不收包（语音控制修过的同款坑）。复用其 jthread 心跳模式：NetSession 后台线程用**独立 socket** 1Hz 发 KEEP（SFML socket 非线程安全，收发socket与心跳socket分离，同 voiceSock/voicePingSock 先例）。拖拽恢复后主循环继续，战斗模拟由 tick 对齐 |
| 快照/输入乱序或丢包 | SNAP 带 tick，客户端只接受更大 tick；INP 无序号，最新到达者生效 |
| 客户端加入时版本不符 | 主机回 ERR，客户端提示后退出加入流程 |
| 同机第二个实例建主局 | 52021 绑定失败 → 提示"端口被占用（已有机局？）"，回标题 |
| Windows 防火墙首次弹窗 | README 说明需允许（专用网络）；被拒则表现为对方扫不到/连不上 |
| 广播被路由器拦截 | `--join <ip>` 显式指定地址兜底 |
| 中途 Esc / 窗口关闭 | 发 BYE 后立刻清理会话与线程，回标题/退出 |
| 语音助手并存 | 语音端口 52017 未接管时自动禁用（现有逻辑），与联机无冲突；52021 被语音占用不可能（端口不同） |

## 8. 测试策略

- **单元测试**（进 `tests/unit_tests.cpp`，不碰 socket）：
  - Battle 模拟：命中扣血；爆炸期间冻结且导弹穿过；爆炸结束回出生点、
    朝向/炮塔重置；无敌期不可被击中；血量归零判负且全场冻结；冷却与
    连发；导弹出界消失；同一输入序列下 stepBattle 结果可复现（主机
    侧确定性）。
  - Protocol 编解码：全部消息 round-trip；坐标/角度量化往返误差 ≤1/16
    单位；截断包/未知 msgId 解析安全返回失败而非崩溃。
- **集成冒烟**（`tools/net_smoke.py`，参照 run_and_shoot.ps1 思路）：
  启动一个主机实例，Python 假客户端完成 广播发现→JOIN→收 SNAP→按
  脚本发 INP→验证快照中己方坦克位移与一次命中扣血。
- **双机验收清单**（人工，写进 README）：发现/加入/倒计时/对战/命中
  流程/无敌帧/判负/双 R 重开/双端 Esc 掉线提示/拖窗口 3 秒不断线。
- 构建验证：`build.bat` 四步全绿（新代码 0 警告；DLL 闭包仍 25 个）。

## 10. 明确不做（YAGNI）

- 不做 2 人以上、观战、AI 补位、合作模式；
- 不做互联网穿透（仅局域网/同网段；`--join` 支持任意可达地址属顺带能力，非目标）；
- 不做断线重连（掉线即结束对局）；
- 不做输入加密/反作弊（局域网熟人对战场景）；
- 不做客户端预测/快照插值（局域网 RTT 无感；InputState 抽象已为将来
  升级留好缝，届时另立设计）。
